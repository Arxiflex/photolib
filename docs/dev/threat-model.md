# Threat model v1

Version 1, for the foundations milestone (M0-29). Review: see the end of this page. Change it in the pull request that
adds a component, moves a trust boundary or changes a control; threat model v2 comes with the pre-1.0 security review
(M10-01). The adversaries and residual risks it builds on are in design 06 §2, the analysis behind them
in the security research.

Each threat below is classified with STRIDE: **S**poofing, **T**ampering, **R**epudiation, **I**nformation
disclosure, **D**enial of service, **E**levation of privilege. Each names its control and what verifies it: a test or
check in this repository, or the roadmap item that must add one. Cryptographic controls cite the known-answer vectors
of [crypto v1](crypto-v1.md), checked against its reference implementation; the kernel runs the symmetric ones (PLB,
PLW, derivations, lockbox, journal) as `kernel/testvectors/crypto.json`, the rest in M6-01.
`tools/tests/test_threat_model.sh` fails the gate when a component lacks one of the six classes, a boundary has no
threat, an adversary has no threat, a cited test does not exist or no threat cites a file of crypto v1 vectors.

## Assets

Originals, renditions and edits; their metadata (capture times, places, faces, captions, albums); keys (account master
key, library, album, file, device and instance keys); credentials and sessions; and the availability of libraries and
their backups.

## Trust boundaries

| ID | Boundary | What crosses it |
|---|---|---|
| TB1 | Person holding a device ↔ the app | Unlock, local data, cached keys |
| TB2 | Device ↔ photolibd over the network | TLS through a reverse proxy; API calls, media, sessions |
| TB3 | Private library ↔ a malicious server | Ciphertext, wraps, signed logs; in private mode the server is not trusted at all |
| TB4 | photolibd ↔ media worker | Untrusted files in; metadata and renditions out |
| TB5 | photolibd ↔ its storage | Database rows, files, objects, dumps |
| TB6 | User ↔ other users | Shared albums, partners, links, contributions |
| TB7 | Browser ↔ the code it is served | The web bundle from photolibd; export viewers from any host |
| TB8 | Project ↔ upstream | Packages, toolchains, CI runners, release hosting |
| TB9 | Photolib ↔ third-party endpoints | Everything in the [privacy manifest](../admin/privacy.md) |
| TB10 | photolibd ↔ an OpenID Connect provider | Discovery, keys, tokens and the claims of the people it vouches for |
| TB11 | photolibd ↔ ML: a remote `ml` node, and the ONNX Runtime library and accelerators a node loads | Self-test reports to the API; model outputs |

## Security review checklist

A pull request that touches one of these areas answers its questions in the description; the threat IDs say what is
at stake. New threats or changed controls update the tables above in the same pull request.

* **Authentication and sessions** (T6, T15, T19, T35, T55, T59–T61, T79, T89, T95): no new way in without rate limits
  and uniform errors; tokens stored hashed, bound to a device, revocable; no secret or token in logs, URLs, errors or
  command lines.
* **Authorisation and sharing** (T16, T37–T41, T52, T53, T57, T63, T81, T92): every new handler, bulk endpoint, stream
  and share path goes through the one authorisation path and has rows in the authz matrix; locked and trashed items stay
  out of shares (trashed ones show only in the trash of whoever may delete them).
* **Cryptography** (T8–T13, T51): only formats in [crypto v1](crypto-v1.md), with new known-answer vectors; no new
  primitive or hand-rolled construction; a released format never changes; secrets are zeroised.
* **Parsing untrusted input** (T7, T21–T25, T33, T58, T66–T68, T72): media is parsed only in the sandbox, by the
  kernel's memory-safe parsers, by the platform's players or, for thumbnails on a device, by its platform's decoders
  and libvips behind its allow-list (ADR-0107); size and count limits come before work; user data never reaches argv,
  HTML or SQL unescaped.
* **Files and storage** (T26–T31, T64, T65, T71, T73–T75, T85, T91): paths stay beneath their root, symlinks are not
  followed, archives are zip-slip safe, writes are atomic, file I/O has a timeout and reads of users' disks a rate
  limit; whatever deletes, trashes, hides or purges in bulk passes `guard::Dry`.
* **Outbound connections and timers** (T48–T50): a new endpoint or periodic task is in the
  [privacy manifest](../admin/privacy.md) with a kill switch, a timeout, a far-future-date test and a self-hosted
  alternative; tests pass with egress blocked.
* **Dependencies and CI** (T42–T47, T62): new dependencies pass `cargo deny` and the licence checks; base images are
  pinned by digest; no new workflow (but `cancel-queue-runs.yml`); job permissions stay read-only.
