# ADR-0025 — Crypto suite v1 specification: the choices behind the bytes

* **Status**: Accepted — 2026-10-15 (roadmap M0-10). The owner confirmed all seven choices as made
  (photolib-design#289).
  The external cryptography audit (M6-14) reviews it and the specification before private mode leaves beta.
* **Requirements**: R-PRIV-1, R-SEC-3, R-REL-2. **Design**: ADR-0010, 06 §3–§5; the
  specification is [crypto-v1](../dev/crypto-v1.md).

## Context

ADR-0010 fixes the algorithms. Turning them into bytes that the Rust kernel, Dart and the viewer produce
identically leaves choices that the design either leaves open (06 §13 question 5, the research's open questions 4–6 and
13) or sketches loosely (the research layouts of §9.2). They must be settled before anything is encrypted, because every
stored object keeps its format forever.

## Decision

We will publish [crypto-v1](../dev/crypto-v1.md) as the normative specification, with known-answer vectors in
`kernel/testvectors/crypto/` generated by a stdlib-only Python reference (`tools/cryptoref/`) that is itself checked
against the published vectors of every primitive. Within it:

* **Headers** carry magic, type, `format_version` and `suite` (15 §1 asks for both): the version fixes the layout, the
  suite the algorithms.
* **Blob chunks use ChaCha20-Poly1305 under a per-object HKDF subkey** (ADR-0010, research §6), not the XChaCha20 that
  the roadmap item names: the random 32-byte salt already makes every payload key unique, so the 12-byte nonce can
  carry the chunk index and final flag, and XChaCha's 24-byte nonce would add nothing. XChaCha20 seals the wraps.
* **X-Wing is pinned to draft-connolly-cfrg-xwing-kem-11**, which is byte-identical to MLKEM768-X25519 (KEM `0x647a`)
  of draft-ietf-hpke-pq-05 (the reference reproduces both drafts' vectors). PLH is HPKE base mode with HKDF-SHA256 and
  ChaCha20-Poly1305. Implementation: RustCrypto `x-wing` with the `hpke` crate; `libcrux` is the fallback. If the RFC
  differs from draft 11 on the wire, that is a new PLH suite, not a change to suite 1.
* **Every symmetric wrap commits to its key** (PLW grows from 112 to 144 bytes), not only blobs: a wrap of the AMK under
  a password-derived key is exactly where partitioning oracles bite.
* **A public-key wrap is accepted only when a signed log entry names its hash** (`add_member`, `new_epoch`,
  `add_device`), because HPKE base mode does not authenticate the sender.
* **Signed bodies are fixed binary layouts**, not CBOR (the research) or protobuf (06 §12, which concerns encrypted
  payloads): signed data must parse exactly one way, the bodies are few and small, and no generated code is needed.
* **Key ids are derived from the key** (`HKDF(k, …/key-id)`) or hash the public key, rather than random, so a reader
  can check that it unwrapped the key it expected; wrap contexts are one fixed 52-byte structure.
* **Argon2id**: one 26-byte parameter record; the account policy is 128 MiB to 2 GiB, 3 to 64 passes and one lane;
  enrolment starts from 256 MiB × 3 and falls back to 128 MiB × 6. Link and export passwords use fixed 64 MiB × 3 with
  the link id as salt. Passwords are NFC-normalised UTF-8.
* **OPAQUE** uses the account's Argon2id parameters as its KSF, so the login record is no cheaper to attack than the
  wrapped AMK; the KEK stays independent of `export_key`.
* **Dedup tokens are HMAC-SHA256**, not BLAKE3, keeping the suite on one hash family.
* **Logs resist a lying server**: readers keep a checkpoint of every log they follow and refuse rollbacks and forks;
  membership logs pin each member's signing key and follow identity-key rotations with `update_member_key`.
* **New members always get the album's history** (back-link chain); a removal must be followed by a new epoch before
  any other membership change, and nobody may upload while it is due. An upload counts only while its uploader may
  still upload, so a removed member cannot backdate one; the admin's client re-signs what the album keeps.
* **64 KiB chunks** stay the default until the streaming spike (M0-33) measures otherwise; readers already accept
  16–22 for `chunk_log2`. Padding is a writer policy outside the format.
* **Ed25519 verification is strict** (`verify_strict`): small-order keys and non-canonical encodings are rejected.

## Consequences

* M0-40 (local data protection) and M6-01 (kernel crypto) implement against fixed bytes and run the same vectors; the
  lockbox, sealed-journal entries, recovery-kit shares and grant statements are added later inside these registries.
* The Python reference doubles as the second implementation that research §6.9 rule 7 asks for. It is slow and not
  constant-time, so it never touches real keys; Argon2id at real sizes is pinned and recomputed only on request.
* Changing any decision above after the first private upload means a new suite or format version, readers for the old
  one forever, and a re-wrap or re-encryption job.
* New-device password unlock runs Argon2id twice (OPAQUE, then the KEK), about two seconds on a phone.
* Every device holds the account's signing key, so a lost unlocked device can sign until the owner rotates it; the
  passcode of ADR-0015 and the rotation on device loss bound that window.

## Options considered

* **Random key ids**: hide nothing the server does not already know and cannot be checked; rejected.
* **CBOR or protobuf signed bodies**: flexible, but several encodings of one statement, a parser in the signature path
  and, for protobuf, generated code for every language before M6; rejected for v1.
* **Commitment on blobs only (the research layout)**: leaves password-wrapped keys open to partitioning oracles;
  rejected.
* **OPAQUE with a light KSF and the KEK carrying the cost**: one Argon2id per unlock, but a stolen database plus OPRF
  seed would allow cheap password guessing against the login record; rejected.
* **`libcrux` X-Wing first**: formally verified ML-KEM, but pre-1.0 and outside RustCrypto; kept as the fallback.
