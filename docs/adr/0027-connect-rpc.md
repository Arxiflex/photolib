# ADR-0027 — Connect on axum with the connectrpc crate, checked by the official conformance suite

* **Status**: Accepted — 2026-10-15. The owner confirmed both choices M0-08 made: `connectrpc` with buffa codegen
  for the server, and the instance id as the epoch
  (photolib-design#293).
* **Requirements**: R-APP-3, NFR-REL-3, F-13. **Design**: 16, ADR-0005,
  [ADR-0019](0019-protobuf-toolchain.md).

## Context

ADR-0005 chose the Connect protocol on axum: the `connectrpc` crate if it passes the official Connect conformance
suite, otherwise a thin in-house implementation. `connectrpc` 0.9 is the Connect project's own Rust implementation,
but it is pre-1.0 and works only with messages generated by buffa, not prost, which ADR-0019 had set up.

## Decision

* **photolibd serves Connect with `connectrpc`**, mounted as the fallback service of its axum router
  (`rpc::connect`). The supported subset is the Connect protocol over HTTP/1.1 and cleartext HTTP/2, binary and JSON,
  identity and gzip, unary calls (POST, and GET for side-effect-free ones) and server-streaming calls.
* **The official conformance suite checks that subset on every build.** `crates/photolib-conformance` serves the
  conformance service through the same `rpc::connect` and `http::serve` as photolibd; `tools/connect_conformance.sh`
  runs the pinned `connectconformance` runner (checked against its SHA-256) for the features in its
  `connect-conformance.yaml`, as part of the gate's `rust` part. At 0.9.1 all 584 cases pass.
* **`GetServerInfo` is the capability negotiation.** It reports `api_version` `1.0`, `min_client_version` `0.0.0`
  (no app is released yet), the capabilities in `rpc::CAPABILITIES` and the epoch. Capabilities are sorted, lowercase,
  dotted names (`sync.stream.v2`); a changed behaviour gets a new name, and a released one stays for the whole
  compatibility window. The first is `error.detail.v1`, the error model below. The epoch is the instance id; the
  restore work must change it on every restore (design 05 §8).
* **Errors are codes and parameters, never prose (F-13).** A service fails with an `rpc::ApiError`: a Connect code,
  a reason code (`asset.not_found`, lowercase dotted words, checked when the error is built) and named parameters,
  sent as a `photolib.api.v1.ErrorDetail` and nothing else. Two guards keep it that way: `server/clippy.toml`
  disallows every `ConnectError` constructor, since each takes a message (`tests/lints.rs` proves the rule fails
  clippy), and an edge layer removes the developer message from every Connect error that still has one, including
  those `connectrpc` writes for a malformed request. gRPC and gRPC-Web, which `connectrpc` would also answer, are
  refused with 415 because their errors carry prose in `grpc-message`.
* **Deprecated procedures say so on every call**: `rpc::DEPRECATIONS` lists them, and their responses carry
  `Deprecation: @<time>` (RFC 9745) and `Sunset: <date>` (RFC 8594); each call is logged with the client's
  `User-Agent`, so administrators see which app versions still use it. The list is empty in v1 so far.
* **Third parties get an OpenAPI 3.1 document** of `photolib.api.v1`, generated by `protoc-gen-connect-openapi`
  with the other code and published with the documentation (`docs/dev/api/photolib.openapi.yaml`). The plugin is a Go
  binary; `tools/codegen.sh install` downloads the pinned release and checks its SHA-256 rather than adding Go.
* **The server's Rust code is generated with buffa and connect-rust** instead of prost, which the kernel keeps
  (amends ADR-0019): `protoc-gen-buffa` messages with proto3 JSON and `protoc-gen-connect-rust` service traits, pinned
  in `tools/codegen.sh` and checked in.
  The conformance protos are third-party test fixtures: they are vendored as `.proto` files and generated at build
  time (`protox`, `connectrpc-build`), which keeps about 950 KB of generated code out of the repository.

## Consequences

* The in-house fallback is not needed; if a `connectrpc` upgrade fails the suite, the gate stops it.
* Pre-1.0 means API churn on upgrades; the conformance run and the server tests bound the risk, and only `rpc` and
  the generated code touch the crate.
* The conformance server is the one Rust crate allowed to send messages, because the suite checks them; photolibd
  itself is conformant with messages omitted, which the protocol allows.
* `GetServerInfo` needs no authentication, so the instance id is public; a UUIDv7, it tells when the instance was
  created and nothing else.
* The gate's `rust` part downloads the runner once (network on the first run), like `buf.sh` and `docs.sh`.

## Options considered

* **A thin in-house Connect layer on prost.** Possible for unary and server-streaming, but prost has no proto3 JSON
  mapping, so JSON (and `google.protobuf.Any` in the conformance messages) would need another generator or our own
  code. Rejected: `connectrpc` passes the suite.
* **Checking in the generated conformance code**, as ADR-0019 does for our own protos. Rejected for 950 KB of
  third-party fixture code that only the test server uses.
